# INTERSPEECH 2026 低延迟语音增强：问题与方法拆解

> 上游：`enhancement-deep-dive.md`（168 篇增强论文分类）
> 本篇对象：全库 27 篇带低延迟标记的论文，其中 **13 篇核心增强**逐篇细读；另含 B/C/D 层 14 篇。

## 0. 先更正上轮的一个结论

上一轮我写「没有任何一篇主张 2 ms 量级」——**这句话对核心增强 13 篇成立，但对全库不成立**。

全库扫描后，**`Don't Listen to Me: A Lightweight, Low-Latency Model for Own-Voice Cancellation`（C 层，目标说话人提取）明确声明 2 ms 算法延迟**。它是目前 INTERSPEECH 2026 里唯一达到本项目 `wiki_low_latency` 量级的论文。

但要注意它的**任务不是通用去噪**：OVC（own-voice cancellation）是"从混合语音中移除已注册的目标说话人，同时保留其余所有人声"，即目标说话人提取的**补集**。任务定义更窄，难度结构也不同（不需要重建被移除的人声，只需抑制）。

**结论修正为**：通用语音增强的最低压到 **8 ms**（RT-Tango）；**2 ms 量级只出现在任务定义更窄的 OVC 上**。

## 1. 延迟数字总表（全库实测）

⚠️ 三类数字必须分开看，论文里经常混着说：

| 论文 | 层 | 数字 | **属于哪一类** |
|---|---|---|---|
| `Don't Listen to Me`（OVC） | C | **2 ms** | 算法延迟 |
| `RT-Tango` | A | **8 ms** | 算法延迟（ultra-low latency） |
| `LaCo-SENet` | A | **12.5–75 ms**（12.5 为全因果） | 算法延迟（可配置） |
| `EffVOC` | A | **20 ms**（对比基线 32 ms+） | 算法延迟 |
| `RT-SEMamba` | A | **25 ms** | 算法延迟约束 |
| `LAU-NetV2` | A | **48.66 ms** | **MCU 上的运行时间**，非算法延迟 |
| `CAPS` | B | **1.36 ms** | **移动端推理时间**，非算法延迟 |
| `HALO` | A | 「不增加」 | 相对增量，未给绝对值 |
| `LCA` | A | 7 档可切换 | 未给绝对数字 |
| `WaveNorm` / `LMPAN` / `HWB-plus` / `DDSN` / `RSE-KSANC` / ANC 增益约束 | A | 仅称「因果/实时」 | **未给数字** |

**关键观察**：13 篇核心增强里，**只有 5 篇给出了具体的算法延迟数字**，其余 8 篇只声称"因果""实时"或"低延迟"而不给量。这说明**低延迟方向目前还没有统一的报告规范**——这与你 `wiki_low_latency` 里"算法延迟/模型耗时/I/O buffer 必须拆开报告"的规则形成鲜明对照，也说明那套规则在学界是超前的。

## 2. 解决了什么问题

### 2.1 需求来源：全部指向可穿戴与实时通信

低延迟不是抽象的工程指标，它的真实来源在这批论文里非常集中：

| 场景 | 论文 |
|---|---|
| 助听器 / 辅听 | `RT-Tango`（低功耗助听器）、`ABSE-NET`（开放耳式） |
| 耳机 | `RSE-KSANC`（实测耳机脉冲响应） |
| 可穿戴传感器 | `LAU-NetV2`（皮肤贴附加速度计 + 可穿戴 MCU） |
| 可穿戴设备通用 | `CAPS`（耳戴设备省电）、`Cloud-Boosted`（可穿戴实时通信） |
| 远场设备回放 | `OVC`（回声往返超过自声失真感知阈值） |
| 实时通信 | `DDSN`（PLC）、`HWB-plus`（BWE）、`LMPAN`（全双工对话） |
| AR/VR | `Sweep-RSE`（ROI 提取） |
| 无人机 | `DroFiT`（旋翼自噪声） |
| 手机 | `NCPSZ`（漏音抑制） |

**没有一个是为了"让离线模型跑得快一点"**。低延迟在这批工作里是**产品约束驱动**，不是学术指标驱动。这解释了为什么它们几乎同时带"部署"标记（13 篇中 8 篇）。

### 2.2 具体问题可以归成四类

**第一类：延迟本身不该是固定值（最有趣的一类）**

- `LaCo-SENet`：现有方法把问题简化成"因果 vs 非因果"的二元选择，但真实预算是一个连续谱。
- `LCA`：助听器要几 ms，电话要几百 ms，而**大多数神经模型只为一个固定 lookahead 训练**，多预算就要训多个完整模型。

这两篇的问题定义是一样的：**把延迟从"设计选择"变成"模型的可调参数"**。

**第二类：传统 STFT 前端锁死了延迟下限**

- `RT-Tango`：双耳助听器的延迟被窗长直接决定。
- `EffVOC`：Griffin-Lim 的算法延迟是"无穷大"，其低延迟变体音质又差；生成式声码器延迟中高。
- `HALO`：STFT 重叠帧带来冗余计算，轻量模型里这个冗余占比很高。

**第三类：长时流式的内存/带宽不可持续**

- `RT-SEMamba`：Transformer 的 KV cache 随序列长度增长，长时流式推理的内存与带宽吃不消。Mamba 每层只传播**固定大小的循环状态**。
- `OVC`：用 Mamba-MinGRU 替换 ConvTasNet 辅助网络。

**第四类：传统信号处理级联本身引入延迟**

- `ANC 增益约束`：微扬声器低频能力有限 → 固定滤波 ANC 会机械过冲 → 常规解法是级联高通滤波 → **但高通滤波的群延迟增加了电子延迟**。
- `RSE-KSANC`：ANC 会连人声一起消掉，常规后置抑制又引入延迟。
- `DDSN`：PLC 里实部虚部联合建模导致相位失配与结构伪影。

### 2.3 一个反直觉的点

**13 篇里没有一篇在解决"低 SNR 抑噪"或"人声保留"**——除了 `RSE-KSANC` 明确以"保人声"为目标。

主流低延迟工作的评价框架是 **延迟–质量权衡**（latency–quality trade-off），而不是**低 SNR 下的人声保真**。`LaCo-SENet` 的卖点是"12.5 ms 下 PESQ 3.35"，`RT-SEMamba` 是"25 ms 约束下 PESQ 3.32"——**它们都在 VoiceBank+DEMAND 这类中低难度集上比 PESQ**。

这意味着：**"低延迟"和"低 SNR 人声保留"在 2026 年还是两个基本不相交的问题**。而 `wiki_low_latency` 恰恰要求两者同时满足——这是一个真实的空白位，但也说明可参照的直接对手很少。

## 3. 用了什么方法

### 3.1 逐篇方法拆解（核心增强 13 篇）

| # | 论文 | 方法核心 |
|---|---|---|
| 11 | `WaveNorm` | 因果端到端时域网络直接从 raw waveform 学时变增益，**去掉手工包络检测器和频谱分析**；49M MACs / 55 KB 内存；作为预处理模块提升 VAD 与降噪 |
| 22 | `HALO` | 半帧率自适应可学习算子：骨干前降帧率、骨干后**恢复到原 STFT 网格**；降/恢复都用轻量动态卷积；不改 STFT 流程 |
| 23 | `LaCo-SENet` | **非对称时域 padding** 重分配过去/未来上下文 + **双缓冲流式**（state buffer 存过去 + lookahead buffer 在输入与特征两级供未来）+ **选择性状态更新**防未来帧泄漏 |
| 24 | `LCA` | 因果模型 + **Latency Control Adapters**，改变可用未来上下文来切换延迟；**batch 内多延迟训练**；单模型 7 档，MACs 恒定，存储参数降 76% |
| 25 | `LAU-NetV2` | **cue-guided FiLM**：把加速度计信号压成「时域 VAD」+「频谱谐波」两类线索，生成 FiLM 参数去调制时频域中间特征；**用调制替代并行编码器/注意力**；46k 参数（少 68×） |
| 26 | `RT-SEMamba` | **因果时频 Mamba 块**（固定大小循环状态）+ **渐进式知识蒸馏**：8 层教师 → 1 层学生，联合蒸馏复数谱输出与中间表示；稳态 RTF 不变下提速 2.75× |
| 27 | `RT-Tango` | 两级分布式架构（ERB 感知特征压缩 + 轻量分组循环掩蔽 + 时间稀疏化）+ **非对称 STFT 把频谱分辨率与算法延迟解耦** + 因果循环推理 + 在线空间统计估计 |
| 30 | `HWB-plus` | **几乎零参数/零算力增量**的改进：Dual-WGMM 基于 STRAIGHT 的周期/非周期分解，ConsWGMM 管高频辅音、VowelWGMM 管中低频元音 + mel 尺度初始化 |
| 32 | `EffVOC` | 在高效低延迟声码器上做**多输入表示统一**（幅度谱 or Mel → WB/FB 输出）；统一框架下比较多模型尺寸 |
| 38 | ANC 增益约束 | 直接在控制滤波器频响上施加**增益约束**（低频段 + 目标降噪频段），**替代级联高通滤波** |
| 39 | `LMPAN` | 多路径对齐（校正参考 / 线性 AEC 输出 / 麦克风的时域与能量失配）+ 注意力动态融合 + 动态目标生成后置滤波；两阶段训练用自监督表征 |
| 42 | `DDSN` | **卷绕相位感知的解耦双流**：幅度与相位独立建模 + SARG（幅度先验引导相位重建）+ 流形约束三角表示保持相位拓扑一致性 |
| 43 | `RSE-KSANC` | 用 DNN **增强参考信号**——抑制参考里的语音、只留噪声，使误差信号中的语音得以保留 |

### 3.2 归纳成六种手法

**① 把延迟变成可调参数**（23, 24）
共同技术：非对称 padding / lookahead buffer / 适配器。这是本批次里**方法学上最有新意的一类**——它改变的不是模型质量，而是"模型与硬件的契约"。对 `wiki_low_latency` 的直接启发：如果延迟是约束，那么**同一模型覆盖多档延迟**比"专为 2 ms 训一个模型"更符合工程现实。

**② 把频谱分辨率与算法延迟解耦**（27 非对称 STFT；32 低延迟声码器；22 半帧率）
这是压到 10 ms 以下的**关键技术**。标准 STFT 的窗长直接决定算法延迟；非对称 STFT / 半帧率算子允许"用长窗拿频率分辨率，但不必等整个窗"。**这三篇是低延迟增强里最值得抄的技术。**

**③ 固定大小循环状态替代 KV cache**（26 Mamba；137 Mamba-MinGRU）
解决的是**长时流式**的内存与带宽，不是单帧延迟。注意：Mamba 在这里的收益是"内存有界"，延迟收益是间接的。

**④ 用轻量调制替代并行分支**（25 FiLM；22 动态卷积；30 零增量改进）
多模态/多分支融合是端侧主要负担。FiLM 把一路信号压成调制参数而非并行编码——46k 参数就是这么做出来的。

**⑤ 用约束或学习替代会引入延迟的 DSP 级联**（38 增益约束替代高通滤波；43 参考增强替代后置抑制）
思路是：传统 DSP 模块（高通、后置滤波器）本身有群延迟，**把它们的功能"吸收"进优化目标或网络里**，就不必付出级联延迟。

**⑥ 蒸馏/剪枝压缩**（26 渐进 KD；39 轻量设计；75 跨模态一致性剪枝）
⚠️ 注意区分：蒸馏降的是**算力**，不必然降**算法延迟**。`RT-SEMamba` 自己就说蒸馏后"保持相同稳态 RTF"，收益是 2.75× 提速。

### 3.3 一个方法学空位

**没有一篇采用扩散或流匹配。** 13 篇核心增强低延迟论文的架构全是判别式的（U-Net、Mamba、TCN、循环掩蔽、动态卷积）或传统 DSP。原因很直接：扩散/流匹配即便做到单步，其单步网络仍是 25–40 ms 前端规模。

这与我上一轮的判断一致，但现在有了更硬的证据：**生成式与低延迟在 INTERSPEECH 2026 里是两个几乎不相交的圈子**。唯一试图靠近的是 C 层的 `MeanFlow-TSE`（一步 MeanFlow 做目标说话人提取），但它也没给延迟数字。

## 4. 对本项目的四条可操作结论

1. **技术可抄的三篇**：`RT-Tango`（非对称 STFT 解耦分辨率与延迟——**最值得直接借鉴**）、`HALO`（半帧率算子，因果且不增延迟）、`LaCo-SENet`（非对称 padding + 双缓冲 + 选择性状态更新，且给了完整的延迟–质量曲线，是很好的对照基线）。
2. **唯一同量级的对手是 `OVC`（2 ms）**，但任务更窄（移除已注册说话人，不需重建人声）。建议精读并明确说明任务差异——**不要被审稿人拿它当"你不是第一个做 2 ms"的反例**。
3. **低延迟 + 低 SNR 人声保留仍是空白**。13 篇里唯一以"保人声"为目标的 `RSE-KSANC` 是耳机 ANC 场景，且没给延迟数字。这是 `wiki_low_latency` 的差异化位置。
4. **评测报告口径可以做成优势**。目前 13 篇里只有 5 篇给算法延迟数字，且普遍把算法延迟、MCU 运行时间、移动端推理时间混着报。`wiki_low_latency` 的"算法延迟/模型 p50-p99/I-O buffer/端到端 capture-to-playback 分开报告"规则如果执行到位，本身就是比现有文献更严格的贡献。

## 5. 局限

- 判定与拆解基于**摘要**，未读全文；方法细节（尤其 23、24、27 的具体实现）需查原文核验。
- 延迟数字为论文自报，未独立复现；不同论文的"算法延迟"定义未必一致（是否含 STFT 窗、是否含 I/O buffer 通常不明确）。
- `LAU-NetV2` 的 48.66 ms 与 `CAPS` 的 1.36 ms 属运行时间，与算法延迟不可直接比较，本报告已分列但未做归一。
- 全库延迟数字扫描基于摘要中 `\d+ ms` 正则，可能漏掉用 samples/frames 表述延迟的论文。
