# 实时语音增强 vs 离线语音增强

## 这是两个完全不同的世界

语音增强的任务目标不同，设计哲学截然不同：

| 维度 | 实时 (Real-Time / Online) | 离线 (Offline / Batch) |
|------|--------------------------|------------------------|
| **典型场景** | 视频会议、电话、直播、助听器 | 录音后期处理、ASR 预处理 |
| **延迟要求** | < 40 ms (端到端) | 无限制 |
| **能否看到"未来"** | ❌ 只能看过去和当前 | ✅ 可看完整音频 |
| **计算硬件** | CPU/嵌入式，无 GPU | GPU 集群 |
| **模型大小** | KB~MB 级别 | GB 级别 |
| **代表性方法** | RNNoise, PercepNet | Conv-TasNet, DPRNN, SepFormer |

## 实时处理的三大约束

### 1. 算法延迟 (Algorithmic Latency)

```
麦克风录音 → [算法处理] → 喇叭播放
            ├─────┤
            算法延迟

总延迟 = 帧长 + 算法延迟 + 传输延迟 + 播放缓冲
```

对视频会议，端到端延迟 > 150ms 时人会感到明显不自然。所以算法延迟常被限制在 **20~40ms**。

**这意味着什么？** 你不能用双向 RNN（BiLSTM/BiGRU），因为双向需要知道"未来"。RNNoise 全部用单向 GRU，这就是为什么。

### 2. 计算复杂度 (Computational Budget)

```
离线场景：             实时场景（移动设备）：
                     
"跑1小时也没关系，      "你只有 10ms 预算，
 用100个GPU也行"        算不出来就丢帧/卡顿"
```

RNNoise 的设计哲学：**每一 FLOP 都有代价**。
- 40 Mflops → 树莓派 3 占 14%
- 1600 Mflops → 根本跑不动

### 3. 内存/缓存限制

```
CPU 存储层次（从快到慢）：
L1 Cache (32KB,  1ns)
L2 Cache (256KB, 4ns)   ← RNNoise 87KB 刚好放下
L3 Cache (8MB,   12ns)
RAM      (8GB,   100ns) ← 大模型权重在这里，每次访问慢 25 倍
```

RNNoise 的 87,503 个权重量化到 8bit 后 ≈ 87KB，存入 L2 Cache。这个设计决策是故意的——**不是"恰好"，而是"精心设计"**。

## 因果性 (Causality) 约束

| 网络类型 | 因果？ | 能用于实时？ |
|----------|--------|-------------|
| 前馈 DNN | ✅ | ✅ |
| 单向 RNN/LSTM/GRU | ✅ | ✅ |
| 双向 RNN/BiLSTM | ❌ | ❌（需要看到整个句子才能输出第一帧） |
| 因果卷积 (Causal Conv) | ✅ | ✅ |
| Transformer (因果掩码) | ✅ | ✅ 但复杂度高 |

## RNNoise 是"实时"的吗？

是的，绝对是。验证：
- **帧长 20ms，帧移 10ms** → 每 10ms 出一帧结果
- **全部用单向 GRU** → 不依赖未来信息
- **40 Mflops** → 低功耗设备可跑
- **单帧处理时间 << 10ms** → 不会产生积压
