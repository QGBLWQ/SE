# 2509.21867 - 速度优化流式设计：可融合性、算子分轴与流式化代价

## 定义

本页从 [[wiki_low_latency/sources/2025/FastEnhancer 2025]]（下称 FastEnhancer 论文）抽象出四条**可复用命题**。它回答的不是"FastEnhancer 好不好"，而是：

> **当"低时延"是硬约束时，哪些设计变量才是真正起作用的？**

论文给出的答案收敛到两点：**（a）决定实际速度的是内存操作与算子可融合性，不是参数量与 MACs；（b）决定延迟的是"是否可缓存 / 是否需 cache"这类结构属性，而不是任何算术量。** 这两点与两个反面对照（DPRNN、DPT）合起来，构成一组相当干净的设计原则。

## 命题 ①：MACs / 参数量是吞吐指标，不是延迟指标；RTF 也是吞吐指标，不是 deadline 指标

这是本页的核心命题。它有两层，必须分开记。

### 1.1 第一层：MACs 低 ≠ 跑得快（算术量 vs 综合开销）

论文给出两组硬证据（均来自 Table 2 / Table 3）：

| 证据 | 数值 | 排除了什么解释 |
|---|---|---|
| **A. 跨模型** | FastEnhancer-B：**262M MACs → RTF 0.022**；GTCRN：**40M MACs → RTF 0.060**；FSPEN：**64M MACs → RTF 0.046**；BSRNN：**245M MACs → RTF 0.059** | 排除"MACS 决定 RTF"——262M 比 40M 高 **6.5×**，RTF 反而低 **2.7×**；245M 与 262M 相近，RTF 差 **2.7×** |
| **B. 同模型、零算术变化** | BN → LN：**参数量 92K 不变、MACs 不变**、SISDR 19.0→18.9、STOI 94.5→94.5，但 **RTF(Xeon) 0.022 → 0.028（+27%）、RTF(M1) 0.026 → 0.029（+12%）** | 排除了"参数/MACs/质量变化导致变慢"——**唯一剩下的解释是算子可融合性与内存操作** |
| **C. 同模型、纯内存变化** | 时间轴 kernel 1→3：Para. 92K→187K、**RTF(Xeon) +27%、RTF(M1) +42%**，而 **SISDR 19.0→19.0、STOI 94.5→94.5 一格不动** | 排除"质量提升的代价"——**只买到了缓存操作的代价** |
| **D. 参数更少却更慢** | DPT 消融：时间轴 GRU→MHSA，**DPT 参数比 RNNFormer 更少**，但因需 **KV cache** 而 RTF 显著升高 | 排除"参数量决定 RTF" |

证据 B 是本命题**最强**的一条：它是**唯一一个让参数量、MACs、质量三项全部保持不变的对照实验**。当一个模型只是把归一化层从 BN 换成 LN，其他什么都不变，速度就掉 27%——这说明**速度的支配因素不在算术量里**。

> [!note] 机理：为什么 BN 能融合而 LN 不能
> BN 在推理期是一个**逐通道的仿射变换** $y=\gamma\frac{x-\mu}{\sqrt{\sigma^2+\epsilon}}+\beta$，其中 $\mu,\sigma$ 是固定的 running statistics。因此它可以被**吸收进相邻的卷积或全连接层**（把 $\gamma/\sqrt{\sigma^2+\epsilon}$ 折进权重、把 $-\gamma\mu/\sqrt{\sigma^2+\epsilon}+\beta$ 折进偏置），推理时**完全不留下额外算子**。
> LN 的统计量是**逐样本、逐时间步动态计算**的（对每个位置的特征维求均值方差），依赖当前输入，**无法预先折叠**——因此推理图上会多出一批 reduce/mean/rsqrt 算子以及随之而来的内存读写。
> 论文原话：「BN can be converted into a simple multiplication-addition operation and fused into adjacent layers at inference time. In contrast, **LN cannot be fused in the same manner, increasing the RTF**。」

> [!note] 这个惩罚是硬件相关的，不是纯算法属性
> 同一次 BN→LN 替换，Xeon 上 +27%，M1 上只有 +12%。同一次 kernel 1→3，Xeon 上 +27%，M1 上 +42%。**两个平台给出的相对代价完全不同**——这说明"算子融合与否"在设计图上是算法属性，但它**兑现成多少墙钟代价，取决于运行时/编译器的算子实现**。本库记录 RTF 时必须连同硬件与运行时一起记（参见 [[wiki_low_latency/concepts/低时延前端与延迟账本]]）。

### 1.2 第二层：RTF 是吞吐，不是 deadline

论文声称在 "streaming condition" 下测 RTF，但**未定义** chunk 大小、是否有 look-ahead、batch 是否为 1、是否把 STFT/iSTFT 计入计时。即便 T 档 RTF = 0.012，它表达的也只是

$$
\text{RTF}=\frac{\text{处理耗时}}{\text{音频时长}}\ll 1
\ \Longleftrightarrow\
\text{平均吞吐足够},
$$

而每帧 / 每 hop 的 deadline 要求的是

$$
\max_t c_t \le \text{budget}(T_{\text{hop}}),
$$

即**最坏情况**必须小于预算。RTF 完全不能替代后者。

> [!important] 本页要把这两句话钉在一起
> **「MACs 低 ≠ 快」** 与 **「RTF 低 ≠ 不超时」** 是两个独立命题，可能同时成立。
> - FastEnhancer 证明了前者（MACs 与 RTF 背离）；
> - 但它**没有**证明后者（无 p50/p95/p99、无 deadline miss、无 underrun）。
> 结论：**用 MACs 排序模型是错的；用 RTF 认证实时性也是错的。** 前者要多测一层硬件，后者要多测一层分位数。

### 1.3 与库内已有条目的衔接

- 本库 [[wiki_low_latency/overview]] 的第 5 条"平均算力 ≠ 可用算力"、第 2 条"算法延迟 ≠ 实时工作点"是本命题的直接对应条目。本篇为它们提供了**目前最完整的一组证据**。
- [[wiki_low_latency/concepts/2408.12425-dynamic-gated-rnn]] 的命题是"**可预测性**比平均值重要"（算力要么固定、要么无用）；本页的命题是"**可融合性**比算术量重要"。两者是同一类论点的两个侧面：都主张**名义算力不决定实时性**，都指向某种"结构属性"。可以合成一条更一般的规则：

> **实时性由结构属性决定，不由算术量决定。** 结构属性包括：算子是否可融合、是否需要 cache、是否产生数据相关的不规则访问、算力是否固定。

## 命题 ②：「可融合性」（fusability）是低时延设计的一等约束

### 2.1 两类"零算术代价、纯延迟代价"的选择

论文把两种结构选择都做成了消融，两者形态完全一致：**参数量与 MACs 几乎不变（或质量不变），速度变差。**

| 选择 | 保留（快） | 替换（慢） | 参数量变化 | 质量变化 | 速度代价 |
|---|---|---|---|---|---|
| **归一化层可融合性** | BN（可融合） | LN（不可融合） | **0**（92K → 92K） | SISDR 19.0→18.9，STOI 不变 | Xeon **+27%**，M1 **+12%** |
| **时间轴卷积是否需缓存** | kernel = 1（免缓存） | kernel = 3（需缓存 k−1 帧） | 92K → 187K | SISDR/STOI **完全不变** | Xeon **+27%**，M1 **+42%** |
| **注意力是否需 KV cache** | 时间轴用 GRU | 时间轴用 MHSA（DPT） | **参数反而更少** | — | **显著升高**（论文未给具体数值） |

三行的共同结构：**代价不体现在算术量上，而体现在"张量是否需要被额外搬运/保留"上。**

### 2.2 机理：内存操作是被忽略的成本项

论文对卷积的说明把机理写得最清楚：

> 「For a time-axis kernel size of $k$, a buffer of $k-1$ past frames is stored and concatenated with the current frame before the convolution operation. The latest $k-1$ frames are then stored in memory for the next computation. **These memory operations significantly increase processing time** (Section 5.2).」

注意论文用的是 **"memory operations"** 而不是 "computation"。在流水线化的推理器上，一次额外的"拼接 + 存储 + 回读"往返，其成本常常**高于**它所要支撑的那点算术量（尤其当算术部分是高度可向量化的 1×1 卷积时）。这解释了为什么 kernel 1→3 会让 PARA 翻倍、RTF 涨 27%，却换不来任何质量提升。

### 2.3 可复用的结构审计清单

本页把上述三类证据抽象成一张**对任何低时延模型都能用的结构审计表**。这个想法直接来自本篇（论文自己只做了其中两项），库里还没有人把它做成通用清单。

| # | 审计项 | 问什么 | 判"危险"的条件 | 本篇证据 |
|---|---|---|---|---|
| ① | **时间轴卷积 kernel** | 是否存在时间轴 kernel $>1$ 的卷积？ | 是 ⇒ 需要缓存 $k-1$ 帧，产生内存往返与延迟 | kernel 3：RTF +27%(Xeon)/+42%(M1)，质量**零收益** |
| ② | **归一化层可融合性** | 用 BN 还是 LN / InstanceNorm？ | LN / InstanceNorm ⇒ 无法折进相邻层，多出 reduce 算子 | BN→LN：参数量/MACs 不变，RTF +27%(Xeon)/+12%(M1) |
| ③ | **注意力是否需 KV cache** | 时间轴上是否用了 self-attention？ | 是 ⇒ 需缓存历史 K/V，且缓存越长越好 ⇒ 内存随流增长 | DPT：参数更少但 RTF 显著升高 |
| ④ | **是否有 global pooling** | 是否存在对整段/整块做池化或全局统计的算子？ | 是 ⇒ 要么聚合未来帧（破因果），要么必须改造 | 本篇**无**此项问题（对照：[[wiki_low_latency/entities/LaCo-SENet]] 的 SCA 用 AdaptiveAvgPool1d，论文自己识别并改掉） |
| ⑤ | **是否有数据相关的不规则访问** | 是否存在 gather/scatter / 依赖输入的行选择？ | 是 ⇒ MAC 计数与实际耗时脱钩 | 本篇**无**此项（对照：[[wiki_low_latency/entities/D-GRU]] 的 top-$A$ 选择、[[wiki_low_latency/entities/Skip-DPCRN]] 的整步跳过） |
| ⑥ | **算力是否固定** | 每帧的算术量是否恒定？ | 否 ⇒ 硬件按最坏情况预留，平均节省兑现不了 | 本篇所有档位均为固定结构 ⇒ 固定（design-level） |
| ⑦ | **是否有全序列统计** | 归一化/注意力是否依赖整段序列长度？ | 是 ⇒ 跨 chunk size 不一致，需改造 | 本篇用 BN running stats ⇒ chunk-size invariant |

> [!note] 这张清单的价值：它把"延迟审计"从"读论文的延迟数字"变成"读论文的层结构"
> 本库现有的大多数模型（包括本篇）**不报告算法延迟**。但清单 ①–③ 可以只靠架构描述判定，**不需要作者配合**。因此它是本库在"延迟账本为空"情况下仍能给出判定的唯一工具。建议对库中所有低时延模型逐一体检（见"对本库的改进建议"）。

## 命题 ③：dual-path 的"两轴应选不同算子"

### 3.1 原则

论文的核心架构主张是：**dual-path 的两条轴不该用同一类算子。** 理由是两条轴的依赖结构本来就不同：

| 轴 | 依赖结构 | 应选算子 | 论文理由（p.2–3） |
|---|---|---|---|
| **时间轴** | **顺序**（$t$ 依赖 $t-1,\dots$） | **递归**（单向 GRU） | 「a GRU is well-suited for streaming inference with minimal latency」——状态大小固定、无 cache 增长、每帧延迟恒定 |
| **频率轴** | **全局、非顺序**（谐波是全局关系） | **注意力**（4-head MHSA） | 「an MHSA is ideal as it can model global relationships and **doesn't require caching**」——在**当前帧内部**沿频率轴做，时间上不看未来，故无需 KV cache |

即：**两条轴各自选"用在该轴上不需要 cache"的那个算子。** 时间轴上递归无需 cache（状态定长）、注意力需要 cache；频率轴上注意力无需 cache（帧内自足）、递归反而**多余地**强加了顺序假设。

### 3.2 两个反面对照，都很干净

论文用两个反例把这条原则反向验证（§5.2，消融三与四）：

| 反面 | 做法 | 违反的是 | 结果 |
|---|---|---|---|
| **DPRNN** | 把**频率轴** MHSA 换成频率轴 GRU | 频率轴用递归 ⇒ **强加顺序假设** | STOI 相近，但 **SISDR 明显下降**（Fig. 3 中 DPRNN 曲线整体在下）；论文结论「superiority of self-attention over a recurrent approach for frequency modeling」 |
| **DPT** | 把**时间轴** GRU 换成时间轴 MHSA | 时间轴用注意力 ⇒ **需要 KV cache** | **参数比 RNNFormer 更少，但 RTF 显著升高**；论文结论「a recurrent approach is a more efficient choice than self-attention for temporal modeling in a streaming scenario」 |

> [!note] 两个反例各自只换来"质量差"或"速度差"，没有一次是"两全"
> - DPRNN 违反原则 ①，代价是**质量**（SISDR 掉），速度上看不出明显便宜；
> - DPT 违反原则 ②，代价是**速度**（RTF 升），参数上反而更少。
> 即：**违反"按轴分配算子"这条原则，会在质量或速度中至少一个维度上付出代价，且不会在另一个维度上得到补偿。** 这是这条原则作为"设计定律"而非"经验技巧"的关键证据。

### 3.3 迁移边界

这条原则**可以直接迁移**到任何双轴（或双因子）结构：

- TF 域 dual-path（时间 × 频率）——本篇与 [[wiki_low_latency/entities/DPCRN]] 家族；
- 通道 × 时间、通道 × 频率；
- 双耳 / 多通道中的 空间轴 × 时间轴；
- 任何"一条轴有任何序、另一条轴只有全局关系"的分解。

**判据只有一个：让每条轴都用"在该轴上不需要 cache"的算子。**

> [!warning] 但这条原则在本库的 2 ms 语境下需要额外一层约束
> "时间轴用 GRU、频率轴用 MHSA"说的是**哪条轴用哪种算子**，它并不解决**帧率**问题。即便每帧内部的处理完全无 cache、延迟恒定，**每帧仍然需要积累一个 hop 的样本**。本篇的 hop 是 16 / 10 / 6.25 ms，**这个下界与算子选择无关**。因此这条原则是"把每帧内部成本压到最低"，不是"把帧率提上去"。

## 命题 ④：「非流式 → 流式」的代价应作为独立报告项

### 4.1 现成的教材：LiSenNet 的 a/b/c 三行

FastEnhancer 论文在 Table 2 里放了同一个模型的**三个版本**，这是本库见到的**最干净的一组"流式化代价"记录**：

| 行 | 脚注 | 是否可流式 | PESQ | SCOREQ | SISDR | BAK | WER |
|---|---|---|---|---|---|---|---|
| LiSenNet^b（脚注 b） | Trained using the official training code. **Not streamable because of input normalization and griffin-lim.** Thus, RTFs are not reported. | **否** | 3.08 | 0.425 | 13.5 | 3.90 | 3.7 |
| LiSenNet^c（脚注 c） | **To make the model streamable**, input normalization and griffin-lim are **removed**. Trained following §4. | **是** | 2.98 | 0.335 | 18.5 | 4.03 | 3.4 |

同一模型、同参数量（37K）、同 MACs（56M），**唯一变量是"去掉 input normalization 与 griffin-lim 使其可流式"**。代价是：

- **PESQ 3.08 → 2.98（−0.10）**
- **SCOREQ 0.425 → 0.335（−0.090，相对 −21%）**
- **SISDR 13.5 → 18.5（+5.0，反而变好）**
- **BAK 3.90 → 4.03（+0.13，反而变好）**
- **WER 3.7 → 3.4（反而变好）**

> [!important] 注意方向并不一致——这不是"单向退化"
> 流式化后 PESQ 与 SCOREQ（自然度类）明显退化，而 SISDR、BAK、WER 反而**改善**。说明"去掉 input normalization + griffin-lim"**改变了误差结构**，不是简单地加了一层损耗：
> - **input normalization 依赖整段输入的统计量** ⇒ 去掉它必然改变谱的动态范围处理方式，可能让模型更保守（保留更多能量 ⇒ BAK 上升、SISDR 上升）；
> - **griffin-lim 是迭代式相位重建**（需要多次 STFT/iSTFT 往返、非因果） ⇒ 去掉它换成模型直接输出相位，PESQ 这类对相位敏感的自然度指标会掉。
> 本库记录时应**并列给出两个版本的全部指标**，而不是只记一个"下降了 0.10"。

### 4.2 可复用命题：把"流式化代价"当成独立报告项

**流式化代价**（streaming-ization cost）指的是：把一个非流式模型改造为可流式（逐帧 / 有限 look-ahead）后，质量指标的变化量。本页主张：

> **非流式基线与它的流式化版本，其数字不应混在同一张排名表里。** 应显式报告"代价"这一栏。

理由有两条：

1. **不可比**——非流式版本享有整段输入或全局归一化带来的信息优势，它的数字是**上界**，不是同一任务的成绩；
2. **代价本身是有信息量的**——LiSenNet 的 −0.10 PESQ / −0.090 SCOREQ 告诉你"这个架构有多依赖非因果组件"；反之，如果一个模型流式化后几乎不掉，说明它本来就基本因果。

> [!question] 但必须先定义清楚"流式"是什么
> LiSenNet 脚注 b 只说 "not streamable because of input normalization and griffin-lim"，**没有说**它的 chunk 大小、look-ahead、或者它被判定为"不可流式"的严格标准。因此这组代价的**口径是不清的**——本库引用时应注明这一点。相比之下 [[wiki_low_latency/sources/2026/LaCo-SENet 2026]] 用「encoder 是否有非因果对称 padding」这一条可核验的判据把 SEMamba / xLSTM-SENet 排除排名，给出了**更严且可复现**的"流式"定义。本库应采用后者的尺子。

### 4.3 与库内相关命题的关系

- [[wiki_low_latency/concepts/2606.19688-latency-configurable-asymmetric-padding]]：那篇把"未来上下文"当成训练期旋钮，量化了"每多一帧 look-ahead 换来多少质量"；本页量化的是"去掉非因果组件要付出多少质量"。**两者是同一个权衡的两侧**：一个问"加未来值多少"，一个问"去未来赔多少"。
- [[wiki_low_latency/concepts/2409.10358-ultra-low-latency-benchmark]]：统一基准的核心困难正是"不同论文的因果口径不同"。本页的命题 ④ 给出一个具体做法：**要求同时报告同一模型的流式/非流式两个数字。**

## 延迟账本与迁移边界

### 可迁移的部分

| # | 可迁移命题 | 迁移方式 |
|---|---|---|
| ① | **MACs/参数量不是速度的序** | 任何"低复杂度"主张都应附一个实测 RTF，并注明硬件 + 运行时 + 是否含前端 |
| ② | **可融合性是设计约束** | 建模型时先问"这个算子在推理期能不能消失"，再问"它值多少 MACs" |
| ③ | **按轴分配算子** | 对每条轴选"在该轴上无需 cache"的算子；判据是"是否有序 + 是否需要跨步状态" |
| ④ | **流式化代价是独立报告项** | 同时报同一模型的流式/非流式版本，并显式给"代价"栏 |
| ⑤ | **结构审计清单（§2.3）** | 只靠架构描述即可对"延迟账本为空"的模型做初步判定 |

### 不可迁移 / 需要先解决的部分

1. **本篇没有延迟数字**。hop 虽然已知（256 / 160 / 100 samples @16 kHz），但论文**从未把它与延迟关联**；STFT 帧锚定（center 与否）**未报告**。因此本页**不能**据此判断它与约 2 ms 的距离。（本库推读：hop 换算为 16 / 10 / 6.25 ms，若 center=True 再加 16 ms 前端 ⇒ 十几毫秒量级。）
2. **"可融合性"的收益是硬件相关的**。同一替换在 Xeon 上 +27%、M1 上 +12%；同一 kernel 改动 Xeon +27%、M1 +42%。**不能把某个平台的比例当常数用**。
3. **面向前向推理的"可融合性"不覆盖训练成本**。BN 与 LN 在训练期的行为完全不同（BN 依赖 batch，LN 不依赖）；"BN 更快"只在下游推理成立。
4. **按轴分配算子这条原则不解决帧率**。帧率由 hop 决定，与算子选择正交。
5. **流式化代价的可比性依赖"流式"定义**。LiSenNet 的判定标准未给出，故 −0.10 PESQ 只能定性使用。
6. **无人声保留证据**。本篇虽报了 SIG/BAK/OVL 与 WER，但**未报告**负 SNR 分层、babble/竞争说话人、false-suppression、SPP/VAD、F0/formant/prosody。因此不能据此判断"流式化代价"是否影响人声保留（见 [[wiki_low_latency/concepts/低 SNR 人声保留评估]]）。

## 对本库的改进建议

1. **把 §2.3 的结构审计清单落成一张跨模型的表。** 对库中所有低时延模型逐一体检 7 项（时间轴 kernel、归一化可融合性、注意力 KV cache、global pooling、数据相关访问、算力是否固定、全序列统计），并标注证据来源（论文明确 / 本库推读）。**这个想法直接来自本篇，库里还没有人做过**——它能立刻暴露出"哪些模型的'快'是有结构依据的、哪些只是声称"。
2. **在 overview 里把"速度证据等级"分级**：① 只有 MACs / 参数量；② 有 RTF 但无非流式口径与硬件说明；③ 有 RTF + 硬件 + 运行时 + chunk 定义；④ 有 p99/deadline。本篇可达 ②–③（RTF + 硬件 + ONNXRuntime 有了，但 chunk 定义缺失）。
3. **建立"流式化代价"字段**：凡库中模型同时有流式与非流式版本的（如 [[wiki_low_latency/entities/PSMSE]] 的 Table 2/3、LiSenNet 的 b/c 行），都应把差值单独记一栏。
4. **提示性追问**：对本篇这类"两轴异质"的架构，值得追问一句——**频率轴注意力既然不需要 cache，它是否已经隐含了"整帧可见"？** 若 STFT 用 center=True，那么"当前帧"本身就已经包含了未来样本，频率轴的无 cache 性质就不能保证严格因果。**本篇没有回答这个问题**（帧锚定未报告），这是本库对它的一个重要保留。

> [!question] 当前缺口
> 1. **"可融合性"缺少跨平台的量化模型**。我们知道 BN vs LN 在 Xeon 上差 27%、在 M1 上差 12%，但**没有**任何论文给出"每多一个不可融合算子值多少 µs"的可迁移公式。
> 2. **"按轴分配算子"只在 TF 域被验证过两次**（本篇的 DPRNN/DPT 对照）。它在通道轴、空间轴上是否同样成立，**未被检验**。
> 3. **"流式化代价"没有统一定义**。LiSenNet 的 b/c 行给了代价，但"什么算可流式"没有可核验判据——本库应沿用 [[wiki_low_latency/entities/LaCo-SENet]] 的"逐层 padding 可核验"尺子来补这个定义。
> 4. **本篇完全没有回答**"频率轴无 cache 的注意力 + center=True 的 STFT 是否仍严格因果"这个问题（帧锚定未报告）。
> 5. **本页提出的结构审计表尚未落到全库模型上**——这是本库可以直接动手做、且不依赖任何新论文的工作。
