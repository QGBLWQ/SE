# 2609.29867 - 算力对齐下的动态深度

## 定义

**算力对齐（compute-matched）**指的是：在比较两种模型时，先让二者的**算力预算相同**（或至少覆盖同一区间），再比较质量。[[wiki_low_latency/sources/2026/Early Exit Compute-Matched 2026]]（下称本篇）把它从"一种实验技巧"提升为**评估动态算力的前提条件**。

**动态深度（dynamic depth）**是条件计算（conditional computation）的一个子类：网络有多个出口，每个输入（这里是每一帧）**在运行时决定走多深**。本篇用的具体形式是 **early exit**——在骨干沿途放 mask head，逐帧选一个。

本页的核心命题是：

> **在算力对齐之前，"动态执行是否值得"这个问题是不可回答的。** 因为动态模型的优势可能来自三个完全不同的来源——① 运行时的自适应、② 这个训练配方本身产出的静态模型更好、③ 评测协议的系统性偏差——而只有把 ① 单独分离出来，"动态"这个词才有内容。

本篇的方法论贡献就是给出了**分离这三个来源的操作手段**：

| 来源 | 分离手段 | 本篇结论 |
|---|---|---|
| ① 运行时自适应 | 与**算力对齐、同配方重训**的静态前沿比 | 几乎为零（< 0.01 PESQ） |
| ② 训练脚手架的收益 | 与**从零训练**的同尺寸静态模型比 | **显著**（同算力最多 +0.11 PESQ，或少 30 % 算力匹配最优） |
| ③ 评测协议偏差 | 把"跳过"实现成**真的跳过状态更新** | 系统性地高估动态模型（本篇改为真跳过，代价 −0.005±0.011 PESQ） |

## 命题 ①：算力对齐是评估动态算力的前提

**观察**：动态 SE 论文极少把"重训的、算力对齐的静态模型"当基线。本篇在 §1 把这一点作为 gap 明说：

> "Dynamic SE is usually compared with **its own exits** [9], while **retrained static models matched for compute are less often used as baselines** [18]."

**为什么这个空白是致命的**：只与"自己的 exits"比，等价于只证明了**同一条 ladder 上深浅之间的 trade-off**，而**完全没有证据**说明这条 ladder 比"另行训练的、算力相同的静态模型"更好。而后者才是用户的真实选择——**要不要为了"动态"多付工程复杂度**。

**本篇怎么做的**：

| 手段 | 具体做法 |
|---|---|
| 覆盖被比较区间 | 训 **12 个静态 Conv-FSENet**（$H\in\{32,64,96,256\}$ × $R\in\{1,2,3\}$，$B=128$），跨 **5.7–41.8 MMAC/s**，**bracket 全部 routed 点（6.6–20.2 MMAC/s）** |
| 同配方 | 静态模型「use the same backbone with the routing and multi-exit machinery removed」，且「follow the same training protocol, with routing-specific losses removed」 |
| 同评测框架 | 同一批 **824** 条测试片段、同一组指标（whole-clip SI-SDR + wideband PESQ） |
| 精确对齐 | **三对**精确算力对齐的 width–depth 对照（检验"同样的算力预算该花在宽度还是深度上"） |

**结论**：算力对齐把结论**从"路由省算力"翻转为"路由只改分配方式"**。

> [!note] 这条命题对本库是一次**口径升级**，不是一个新发现
> 本库在 [[wiki_low_latency/concepts/2207.11108-inference-skipping-parallel-rnn]] 里已经写过"平均省 33 % ≠ 峰值省 33 %"，在 [[wiki_low_latency/concepts/2408.12425-dynamic-gated-rnn]] 里写过"每步算力恒定 vs 随步波动"。**两条都在问"省下的算力能不能兑现"**。
> 本篇提的是**第三个问题**：**"省下来的算力换到的质量，别人用固定算力也能达到吗？"** —— 这个问题与前两条**正交**，本库此前**从未系统提出过**。因此本页把命题 ① 记为本库的**新增审计维度**（见"对本库的改进建议"）。

## 命题 ②：早退的增益可能来自"训练脚手架"，而非"运行时适应"

**这是本篇最核心、也最容易被误读的一条。**

**第一步：暴露问题。** 本篇的 knee target 定义是「最便宜的、误差在最优 $\varepsilon$ 之内的 exit」——它**从当前的 exits 出发定义，因此不要求质量随深度改善**。而当只训练 SE 任务损失时，「**on nearly half of the frames, a deeper exit performs worse than its previous one**」（引 [7] 的 "overthinking" 现象）。于是：

> "**a policy may appear useful simply because it avoids harmful deeper exits, rather than because it assigns less compute to frames that genuinely need less processing.**"（p.2 §2.3）

**第二步：把成分分离。** 论文用 **mono-repair** 做分离——冻结 backbone / frontend / policy，**只微调 4×33k 参数的 exit heads**，加单调性正则（Eq. 7）。修复之后，每个 exit 都能**单独作为一个静态模型**部署，于是可以画出第二条前沿：**repaired 前沿**。

**第三步：比较三条前沿。**

| 对照 | 结果 |
|---|---|
| routed **vs** 专用静态（从零训练） | routed 明显占优：routed H=64 **2.719 PESQ @ 8.48 MMAC/s**，同算力静态前沿约 **2.60**；差距随算力增大而缩小，但 routed 始终在上方 |
| routed **vs** mono-repaired | **几乎重合**：共同区间 PESQ 差 **< 0.01**；三个点 8.48 / 12.18 / 20.22 MMAC/s 上分别 **+0.009 / −0.001 / +0.007** |

**结论**（论文原话）：

> "**per-frame routing does not raise the best quality attainable at a given compute budget, but importantly it does not noticeably lower it either.**"

**推论（本页的读法）**：

~~~text
"动态执行的价值"必须拆成两项分别计量：

  ┌─ (A) 运行时适应 ────────────── 本Δ ≈ 0（< 0.01 PESQ）
  │      "把算力花在需要它的帧上"
  │
  └─ (B) 训练脚手架 ────────────── 本Δ 显著（同算力最多 +0.11 PESQ；
          "一次训练、多出口互相监督，         少 30 % 算力匹配最优）
           逼出的静态模型比从零训练更好"

  评测方法：把 exit ladder 拆成一组静态模型（mono-repair），
            再与"同算力、同配方、从零训练"的静态前沿比
            → (A) 消失，(B) 留下
~~~

**为什么 (B) 会存在**：deep supervision（Eq. 4）让每个 exit **都被独立监督**，一个浅出口从深出口的梯度里获得了额外的信号；同时，一次训练产出一族模型，其**有效训练量**高于逐个训练。论文对此的措辞是「**more Pareto-efficient than their equivalently-sized counterparts trained from scratch on the same budget**」。

> [!note] 这条命题对"动态算力"这条线是一个**范式性的重新定位**
> 本库已收录的动态算力工作，都把价值定位在 **(A)** 上：
> - [[wiki_low_latency/entities/Skip-DPCRN]]：「平均省 32.8 % 算力」（运行时跳过）；
> - [[wiki_low_latency/entities/D-GRU]]：「每步只更新 50 % 神经元」（运行时稀疏）；
> - [[wiki_low_latency/entities/RT-Tango]]：「固定间隔复用 mask」（运行时复用）。
>
> 本篇说：**把 (B) 分离出来之后，(A) 在语音密集数据上几乎为零**。
> **这不否证前三篇**（它们的场景/任务/硬件不同，且都没做这个分离），但它给出了一条**新的测量要求**：**任何声称"动态执行有用"的工作，都应先证明 (A) ≠ 0**，否则它测到的可能只是 (B)。

## 命题 ③：名义 MACs 在真实加速器上会给出错误排序——**但机理与 FastEnhancer 不同**

**观察（本篇，真机 int8 实测，STM32N6570-DK）**：

| 事实 | 数据 |
|---|---|
| 每 MMAC 执行时间跨 **1.7×** | **82 – 137 µs/MMAC**（10 个拓扑） |
| 相同名义算力、不同运行时 | $(H{=}32,R{=}2)$ 与 $(H{=}64,R{=}1)$ 的 **MACs 与参数量完全相同**，却 **1.001 vs 0.751 ms/frame**（差 **0.250 ms**） |
| MACs 给出**错误排序** | $(H{=}96,R{=}1)$ 比 $(H{=}32,R{=}2)$ **MACs 多 21 %**，却**快 15 %** |
| 加宽 vs 加深 | 「increasing $H$ from 32 to 256 raises the **MACs within a stack by 8×**, but its **measured latency by only 3.1×**」（**3.1× 无法由 Table 1 复现**，见实体页 [!question]） |

**本篇给出的机理**（p.3 §4.2）：

> "**Depth is particularly costly because each additional stack requires another accelerator launch, while increasing width makes better use of the NPU.**"

**与 [[wiki_low_latency/concepts/2509.21867-speed-optimized-streaming-design]]（FastEnhancer）的机理差异——本页认为必须写清**：

| 维度 | FastEnhancer（2509.21867） | 本篇（2609.29867） |
|---|---|---|
| **硬件层级** | 单线程 **CPU**（Intel Xeon Gold 6248R / Apple M1） | **MCU + NPU**（Cortex-M55 + Neural-ART） |
| **量纲** | **RTF**（吞吐：处理时长 / 音频时长） | **ms/frame**（延迟：每帧执行时间） |
| **归因机理** | **算子可融合性 / 内存操作**：BN 可融合进相邻层，LN 不可；时间轴 kernel>1 需缓存 $k-1$ 帧 | **accelerator launch 次数 / NPU 利用率**：每加深一层就要多一次加速器启动；宽度更能吃满 NPU 的数据并行度 |
| **证据形式** | 消融表：BN→LN 在 **Para 与 MACs 完全不变**下 RTF +27 %（Xeon）/ +12 %（M1）；kernel 1→3 使 Para 翻倍而 SISDR/STOI 一格不动 | 实测表：10 个拓扑的 **µs/MMAC 跨 1.7×**；同 MACs 的两种拓扑差 33 % 时间 |
| **共同结论** | 参数量与 MACs **都不能预测速度** | 同左 |

**两者的机理是"同一现象在两个硬件层级上的两次显影"**：

~~~text
        "MACs 不能预测速度"
                 │
     ┌───────────┴───────────┐
     ▼                       ▼
  CPU 层（算子级）        NPU 层（图层级）
  ─────────────          ─────────────
  融合性 / 内存操作        加速器启动次数 / 利用率
  BN 能融合、LN 不能       每层 stack = 一次 launch
  kernel>1 → 缓存 k-1 帧   宽度 ↑ → NPU 并行度 ↑
  ─→ FastEnhancer          ─→ 本篇
     (RTF, 单线程 CPU)         (ms/frame, MCU + NPU)
~~~

> [!note] 这条差异对本库的工程意义：**"结构审计清单"需要一个硬件相关的维度**
> [[wiki_low_latency/concepts/2509.21867-speed-optimized-streaming-design]] 已给出一份"结构审计清单"（算子可融合性、缓存需求、KV cache、算子选择等）。
> 本篇表明：**在 NPU 类硬件上，"图的段数"本身就是速度的一等约束**——因为**每一段图都要一次 accelerator launch**。这条在 CPU 上不存在（CPU 上没有"启动一次算子"这种粒度成本）。
> 本页因此建议把「**图的段数 / accelerator launch 次数**」作为该清单的**第 8 项候选**（见"对本库的改进建议"）。

## 命题 ④：评测协议本身会制造虚假的动态收益

**本篇指出的具体偏差**（p.4 §4.3）：

> "This is far more realistic than **common offline evaluation protocols, which compute the routed output as a gated sum, thereby effectively updating each exit even when unused**."

**问题拆解**：常见的离线协议把 routed 输出算成 **gated sum**——对全部 exit 的输出做门控加权求和。这个算法的**副作用**是：

- 每个 exit 的**前向计算都被执行了**（否则拿不到它的输出）；
- 因此每个 exit 的**内部状态（RNN 隐状态、卷积 ring buffer）都被更新了**。

于是，在这种协议下评测出来的"动态模型"：

- **它从未经历过"状态冻结"**；
- 它的质量是**一个从未在真实部署中出现的系统的质量**；
- 更微妙的是：**gated sum 是对多个深度的输出做加权平均**，这本身是一个**集成（ensemble）效应**——而真实的 routed 执行**只会跑一个 exit**。

**本篇的做法**：真的不更新。被跳过的 stack 的 ring buffer **保持不动**；当它下次恢复时，「its state reflects **the most recent frames processed by that stack rather than the most recent input frames**」。

**代价**（如实报告）：

| 指标 | 代价 |
|---|---|
| PESQ | **−0.005 ± 0.011**（824 条片段） |
| SI-SDR | **0.14 dB** |
| 决策 | **routing decisions bit-identical across arms**（两个 arm 的决策完全相同） |

**为什么 bit-identical 很重要**：它把上面这两行数值变成**干净的单变量对照**——唯一的变量是"状态是否更新"，而不是"决策 + 状态"的混合效应。这是本篇在方法学上很讲究的一处。

**补救尝试与结论**：

> "**Neither zero-order hold nor propagating the last computed state to deeper stacks [33] recovers the lost quality.**"（引 [33] = Depth-adaptive transformer, ICLR 2020）

**结论**：**保持跳过状态不变**（这也是导出图的既有行为，**无需改固件**）。

> [!warning] 这条命题直接指向本库的**待审计项**
> 本库收录的动态算力工作（[[wiki_low_latency/entities/D-GRU]]、[[wiki_low_latency/entities/Skip-DPCRN]]、[[wiki_low_latency/entities/RT-Tango]] 等）**都没有报告它们如何处理"被跳过部分的状态"**：
> - Skip-DPCRN 在串行宿主上会"输出冻结"（其页面已记录 mask 停更的伪影）；
> - D-GRU 的跳步是**神经元级**，$h_t$ 始终向后传递（**无状态冻结问题**，其页面已论证）；
> - RT-Tango 的 FRS 是**固定间隔复用 mask**，被复用的帧是否更新状态**未报告**。
>
> 因此本页建议：**把"被跳过单元的状态是否更新"列为待审计项**，凡未报告者默认其评测可能偏乐观。
> **注意区分两种偏差**：
> | 偏差 | 方向 | 本库已有记录 |
> |---|---|---|
> | **平均值掩盖峰值** | 高估"deadline 余量" | [[wiki_low_latency/concepts/2207.11108-inference-skipping-parallel-rnn]]（平均省 33 %、峰值只降 15 %） |
> | **协议掩盖跳过** | 高估"动态模型的质量" | **本篇新增** |
> 两者都属于"评测协议制造虚假收益"，但**一个是算力口径、一个是状态口径**。

## 命题 ⑤：把 host 侧统计量与 state tensor 显式化，是动态图可部署的前提

**本篇的工程做法**（p.4 §4.1）：

| 做法 | 原文 | 解决什么 |
|---|---|---|
| STFT/iSTFT/masking 留在 host | "We keep the **STFT, iSTFT and masking on the host (no NPU FFT)**" | NPU 没有 FFT 算子 → 不硬塞进图 |
| ring buffer 导出为**显式 state tensor** | "export **ring buffers as explicit state tensors**, making each graph **a pure per-frame stateless function**" | ① 图变成纯函数 → 可静态编译；② 状态张量显式 → 量化范围可标定 → 可 int8；③ 静态 shape → 可上 NPU |
| 图切分与共享 | **9 张子图**（frontend / router / 3×stack / 4×head）；「different depths **share the same frontend and stack graphs**」 | 整族**只占一条 ladder 的存储**，而不是多份独立模型 |

**为什么"显式 state tensor"是**动态**图可部署的**前提**（而不只是优化）：

- **动态图的问题**：图形的执行路径随输入变化。工具链若要 lower 一张"有时跑 2 层、有时跑 4 层"的图，必须支持**控制流**——而主流 MCU 工具链**不支持**（本篇的原文：主流 edge 工具链「lower **one static graph**」）。
- **解法**：把"深度可变"从**一张图内部的控制流**，转化为**host 侧的图间派发**。host 决定跑哪几张子图，NPU 只负责执行固定形状的纯函数。
- **前提**：若要 host 能派发，则**跨帧状态必须能被 host 携带**——因此必须**显式化**为图输入/输出张量。若状态藏在图内部的隐式缓存里，host **无法**在"跳过一段图"后保证状态一致性。

> [!note] 这条工程做法与本库其他论文的努力是**同一类动作**
> | 论文 | 工程动作 | 换到了什么 |
> |---|---|---|
> | [[wiki_low_latency/sources/2026/LaCo-SENet 2026]] | 逐层 padding 分配式 + 状态选择算子 | **确定可复算的算法时延** |
> | [[wiki_low_latency/sources/2025/FastEnhancer 2025]] | 全模型 BN + 推理期融合；时间轴 kernel=1 | **可融合、免缓存的算子** |
> | **本篇** | **ring buffer 显式 state tensor + 图切分** | **可静态编译、可 int8、可上 NPU 的动态图** |
>
> 三者的共同点：**把"运行时才能确定的东西"提前变成"编译期就能确定的东西"**。这是本库低时延工程的一条**通用方法论**，本页建议把它记为该议题的横切主题。

## 与库内已有条目的关系

### 与 [[wiki_low_latency/concepts/2408.12425-dynamic-gated-rnn]]（D-GRU）的关系

D-GRU 页的核心命题是「**"跳多少"的可预测性比平均值更重要**」——它主张**固定比例**的神经元级稀疏优于 Skip RNN 的波动式跳过，因为只有前者能降低**最坏情况**算力。本篇在本页命题 ④ 里补上了**另一个不可预测性来源**：

~~~text
"动态执行的可预测性"有两个层面：

  (i)  算力层面：最大每步算力是否降低？      ← D-GRU 的命题
        D-GRU：固定 A ⇒ 降（设计保证，未测量）
        Skip-RNN：波动 ⇒ 不降

  (ii) 状态层面：被跳过的单元其状态如何演化？  ← 本篇的命题
        本篇：真的不更新（并量化了代价）
        常见协议：gated sum ⇒ 实际上全都在更新 ⇒ 评测偏乐观
~~~

D-GRU 的神经元级跳过**天然不需要担心 (ii)**——$h_t$ 始终存在并向后传递（其页面已论证）。所以**两条命题互不冲突、恰好互补**：D-GRU 排除了算力层面的不可预测性，本篇排除了状态层面的评测偏差。

**合成一条更一般的规则**：

> **对任何"跳过"机制，都要问两个问题：① 最坏情况的算力是否真的降了？② 被跳过单元的状态是否真的没动？两个问题的答案都必须来自测量，而不是来自平均值的论证。**

### 与 [[wiki_low_latency/concepts/2207.11108-inference-skipping-parallel-rnn]]（Skip-DPCRN）的合成

该页的核心是「**平均省 33 % 但峰值只降约 15 %**」。本篇贡献的是**第三个尺度**：

| 尺度 | 问题 | 出处 |
|---|---|---|
| **峰值 vs 平均** | 省下的算力在 deadline 上兑现得了吗？ | [[wiki_low_latency/concepts/2207.11108-inference-skipping-parallel-rnn]] |
| **恒定 vs 波动** | 能不能把最坏情况压低（而不是只压低平均）？ | [[wiki_low_latency/concepts/2408.12425-dynamic-gated-rnn]] |
| **对齐 vs 未对齐** | 省下的算力买到的质量，静态模型花同样的算力能买到吗？ | **本篇（命题 ①）** |
| **真跳过 vs 协议跳过** | 被跳过的状态真的没更新吗？ | **本篇（命题 ④）** |

**四个尺度合起来构成一个完整的"动态执行审计框架"**——本页建议本库以此作为该议题的标准提问清单（见"对本库的改进建议"）。

### 与 [[wiki_low_latency/concepts/2509.21867-speed-optimized-streaming-design]]（FastEnhancer）的结构审计清单对照

FastEnhancer 概念页给出的结构审计清单（本页复述其要点）：**算子可融合性**、**缓存需求（kernel>1 需要 $k-1$ 帧）**、**KV cache 需求**、**两轴用不同算子**（时间 RNN / 频率 attention）、**内存操作量**。

**本篇提出的新增候选**：

| 新增候选项 | 为什么 | 本篇证据 |
|---|---|---|
| **⑧ 图的段数 / accelerator launch 次数** | 在 NPU 类硬件上，**每一段图都要一次加速器启动**；这是 CPU 上不存在的成本 | $(H{=}32,R{=}2)$ 与 $(H{=}64,R{=}1)$ 同 MACs 同参数量，**1.001 vs 0.751 ms/frame**；$(H{=}96,R{=}1)$ MACs 多 21 % 却快 15 % |
| **⑨ 被跳过单元的状态更新语义**（本页附加） | 决定评测结果是否可迁移到部署 | gated sum → 真跳过，代价 −0.005±0.011 PESQ，**决策 bit-identical** |
| **⑩ 量化后路由行为是否漂移**（本页附加） | 动态决策是数据相关的，量化可能改变它 | 「quantization shifts routed compute by **at most 2 %**」 |

### 与 [[wiki_low_latency/entities/RT-Tango]] 的关系

RT-Tango 用 **FRS 固定间隔复用 mask** 省算力，并在消融里对比过 learned skipping / SkipRNN / TinyLSTM（learned skipping 反而伤害 MN-DNN）。这与 **[wiki_low_latency/concepts/2408.12425-dynamic-gated-rnn]** 的"固定比例优于学出来的波动"**互相印证**。

本篇提供了一个**新的解释角度**：学出来的 skipping 之所以不划算，可能不只是因为"算力波动"，还因为**它所省下的算力并没有买到质量**——而它看起来有用，可能是因为**在回避有害的深出口**（命题 ②）。**这可能正是 learned skipping 在这些消融里表现不佳的原因。**

## 对本库的改进建议

### 建议 1：把"算力证据等级"从四级扩展为**五级**

本库现有的算力证据记录方式混用了多种口径。本页建议明确分级（沿用 [[wiki_low_latency/entities/FastEnhancer]] 与 [[wiki_low_latency/entities/D-GRU]] 的对照经验）：

| 等级 | 判据 | 本库示例 |
|---|---|---|
| **L0 名义 MACs / FLOPs** | 只有解析计数，无任何测量，无目标硬件 | [[wiki_low_latency/entities/D-GRU]]（135.32 M MAC/s，无 RTF） |
| **L1 理论延迟推导** | 有窗长/hop/padding 的逐层推导式，但无测量 | [[wiki_low_latency/entities/LaCo-SENet]]（逐层 padding 分配式） |
| **L2 CPU/GPU 吞吐（RTF）** | 有真实测量的吞吐量，但**量纲是 RTF 不是延迟**（含分位数者另注） | [[wiki_low_latency/entities/FastEnhancer]]（RTF 单值，无 p99） |
| **L3 真机延迟（**含硬件**）** | 在**目标硬件**上测 ms/frame 或算法时延，报平台与频率 | ——（本库此前无此级） |
| **L3q 真机延迟 + 量化** | 在 L3 基础上**额外**报告量化方案与量化误差，且**逐图/逐配置**给出 | **本篇**（STM32N6570-DK，int8，10 个拓扑 + 9 个部署模型，µs/MMAC，量化误差 −0.03~+0.01 PESQ） |

**理由**：L0→L1→L2 的差别是"测量与否"；L2→L3 的差别是"**量纲**"（吞吐 vs 延迟）；L3→L3q 的差别是"**真实可部署性**"（未量化 vs 量化）。这四级里**每一级都不能被上一级替代**，而本库同时存在四级的样本，正好需要一把尺子。

> [!note] 新增的两个子字段
> - **L2/L3 都必须注明"平均值 / p50 / p95 / p99"**：本篇只有**平均**（"per-frame mean latency"），因此它的 L3q 等级**不代表 deadline 已通过**；
> - **L3/L3q 必须注明"是否端到端"**：本篇**不是**（STFT/iSTFT/masking 留在 host，未计入）。

### 建议 2：把"gate sum 式评测 / 跳过状态语义"列为**待审计项**

对库内所有涉及"跳过/复用/早退"的论文，补一个字段：**"被跳过单元的状态是否更新？"**。取值：

- `真跳过`（跳过即不更新）→ 本库示例：本篇、[[wiki_low_latency/entities/D-GRU]]（神经元级，$h_t$ 始终传递）；
- `协议跳过`（评测时仍在更新）→ **待审计**；
- `未报告` → **默认按偏乐观对待**；
- `不适用`（无状态 / 每次重置）。

**理由**：本篇明确证明这个选择会造成**可测的质量差**（−0.005±0.011 PESQ），而且这个差值在**决策 bit-identical** 的干净对照下取得。因此它不是一个可以忽略的实现细节。

### 建议 3：把"accelerator launch 次数"纳入**结构审计清单**

如命题 ③ 所述，建议在 [[wiki_low_latency/concepts/2509.21867-speed-optimized-streaming-design]] 的结构审计清单里新增第 8 项。同时给清单加一个**硬件维度标注**：

| 清单项 | 在 CPU 上 | 在 NPU/MCU 上 |
|---|---|---|
| 算子可融合性（BN vs LN） | **关键** | 关键 |
| 缓存需求（kernel>1） | **关键** | 关键 |
| KV cache 需求 | **关键** | 关键 |
| 内存操作量 | **关键** | 关键 |
| **图的段数 / accelerator launch 次数** | 不适用 | **关键**（本篇证据） |
| 状态导出是否显式 | 不适用（可用隐式状态） | **关键**（NPU 只吃静态图） |

**理由**：清单若不带硬件标注，会在跨硬件比较时给出错误建议（例如"加深一层很便宜"在 CPU 上可能成立，在 NPU 上代价显著）。

### 建议 4：把"算力对齐 + 同配方重训"写进**动态算力类论文的入库门槛**

对库内凡声称"动态/条件计算带来收益"的论文，要求其明确回答：

1. 是否与**算力对齐的静态基线**比？该基线是否**同配方重训**（而非引用他人数字）？
2. 若否，则其"收益"应记为**未分离**（可能是训练脚手架的功劳）。

**理由**：本篇证明这两个来源的贡献量级相差一个数量级（(A) < 0.01 PESQ vs (B) 最多 +0.11 PESQ）。不分离就无法判断方法的真实价值。

### 建议 5：把"混合精度下的路由漂移"列为可选审计项

本篇报告「quantization shifts routed compute by **at most 2 %**」。这是一个**动态模型特有的**风险：**动态决策依赖数据，量化会改变数据的数值分布，因此可能改变决策**。建议对库内动态模型补记此项（无则记"未报告"）。

## 时延账本与迁移边界

| 项目 | 本篇证据 | 本 Wiki 判定 |
|---|---|---|
| 采样率 / 窗长 / hop | **16 kHz**；**512 样本窗 = 32 ms**；**50 % overlap ⇒ hop 256 = 16 ms**；$F=257$ | 窗长与 hop 明确；**ms 换算为本页推得** |
| **STFT center / 帧锚定 / padding** | **未报告** | `unreported`：**决定性缺口**——若 `center=True` 则前端含 16 ms 未来样本 |
| 逐层 padding certificate | **未给** | `unreported` |
| 感受野 | **1 / 15 / 29 / 43 帧**，head 0 memoryless；**方向性未说明** | 数值明确、方向 `unreported`（本页给出一个自洽的 look-back 推导，见实体页） |
| 因果性 | 「**All networks are causal at a 16 ms hop**」——**全文唯一一句** | **`paper-claimed-causal`** |
| 跳过机制的结构性保证 | 被跳过的 stack 状态**不更新** ⇒ 输出只依赖该 stack 真正处理过的帧 | **本库认为这强于一般的"我们用因果卷积"，但论文未把它写成因果性论证** |
| 算法延迟（论文口径） | **未报告**——论文没有这个概念与数值 | `unreported` |
| 每帧执行时间 | **实测**：Table 1 **0.640–3.584 ms/frame**（10 个 int8 单图）；Table 2 **0.751–2.472 ms/frame** | **L3q（本库最高等级）**；**但是平均值** |
| p50 / p95 / p99 | **全部未报告** | 未验证 |
| deadline miss / underrun | **未报告** | 未验证 |
| 是否端到端 | **否**（STFT/iSTFT/masking 在 host） | **本库特别标注** |
| 平台 | **STM32N6570-DK**：Cortex-M55 **800 MHz** + Neural-ART **1 GHz** | 明确 |
| 量化 | **int8**，post-training，per-channel scaling + entropy calibration | 明确；量化误差 **−0.03 ~ +0.01 PESQ** |
| 峰值 RAM/SRAM | **未报告**（只说编译器报告含 memory requirements） | 未验证 |
| 功耗 | **未报告** | 未验证 |
| 人声保留 | 只有 **whole-clip SI-SDR** 与 **wideband PESQ**（824 条） | **无 SIG/BAK、无 WER、无负 SNR 分层、无 false-suppression、无 F0/prosody** |

**可迁移的部分**：

1. **"算力对齐 + 同配方重训"这一条对照设计**可以直接搬到任何"动态/条件计算"方法的评估上——它是**唯一能把训练脚手架收益与运行时适应收益分开**的手段（命题 ②）。
2. **"mono-repair 作为分离工具"这个操作**是通用的：把多出口网络的每个出口**冻结 backbone 后微调成可独立部署的静态模型**，就得到第二条前沿。它对 early-exit、slimmable、elastic 网络都适用。
3. **"state tensor 显式化"这套工程做法**可直接迁移到任何要在 NPU/MCU 上跑流式模型的场景（命题 ⑤）。
4. **「图的段数 = accelerator launch 次数」这条成本模型**可直接用于 NPU 类硬件上的架构搜索（命题 ③）。
5. **"跳过即不更新"这一协议选择**及其代价量化方法（bit-identical 决策的对照）可直接复用（命题 ④）。

**不可迁移 / 需要先解决的部分**：

1. **结论的适用范围很窄**：论文**自陈**主张只限于**语音密集数据集**（VoiceBank–DEMAND），长停顿工作负载不在研究范围内。因此**不能**把"逐帧早退不值"推广到"有长停顿/难度变化的流"上——这是论文明确列出的 future work。
2. **只有平均延迟**：无 p99、无 deadline miss，因此"16 ms hop 下有富余"**不能**被本页断言。
3. **不端到端**：Table 1/2 不含 STFT/iSTFT 的耗时，因此**不能**当作 2 ms 级系统的候选。
4. **单数据集、单任务**：全部结论建立在 VoiceBank–DEMAND 的 824 条测试片段上；**无噪声类型分层、无负 SNR 分层**。
5. **人声保留维度几乎空白**：只有 SI-SDR + PESQ，无法判断 §5 那条"1.0 dB SI-SDR 下降"落在噪声残留还是语音损伤上。

> [!question] 当前缺口
> 本篇证明了"在**语音密集**数据集上，逐帧深度选择**不提高**给定算力下的质量上限"，但它**没有回答反向问题**：
> ① 在**稀疏工作负载**（长停顿、难度变化）上，(A) 运行时适应是否显著非零？——论文自己把它列为"an important next step"，且**明确说长停顿不在本研究范围内**；

> ③ **p99 是多少**？在 16 ms hop 下，"平均 0.930 ms/frame"是否意味着最坏帧也安全？**没有任何分布数据**；
> ④ 被跳过的 stack 状态长期不更新，在**长流（分钟级）**下会累积多大的状态陈旧度？——论文的 Fig. 4 只演示了 8 秒。
